# Pre-release review: findings and what was done

Three reviews ran before the first commit (2026-10-16): a fresh AI agent following AGENTS.md in a
clean copy, a publishing and privacy review, and a benchmark-correctness review. Every finding is
listed below with what was done. "Applied" means the suggested fix, or an equivalent one, is in this
commit. Rejected parts have a reason.

Tests that cover the fixes: `tests/test_review_fixes.py` (new) and the new tests at the end of
`tests/test_runner_unit.py` and `tests/test_workloads_unit.py`.

## F. Fresh-agent review (following AGENTS.md as an AI agent would)

| # | Sev. | Finding | Done |
|---|---|---|---|
| F1 | high | `quick`/`full` outlive agent tool time limits; a killed runner left its child running (own process group), holding the GPU; the rerun then measures false `oom`/split rows, which resume caches | **Applied.** (a) Every process the runner starts gets `AGBENCH_PARENT=<pid>:<start time>`; `agbench.child` and the `doctor`/`fetch`/`prepare` commands exit within 1 s when the runner is gone (polling thread on every OS, `PR_SET_PDEATHSIG` on Linux), and on Windows the runner puts its children in a kill-on-close Job Object. (b) A new run first stops leftover `agbench` processes that point into its results folder (it holds the lock, so none can be live). (c) AGENTS.md step 6: run in the background with output to a file, poll it, never kill a running suite; rerun resumes. ## R. Benchmark-correctness review

| # | Sev. | Finding | Done |
|---|---|---|---|
| R1 | medium | Ratios against our training logs compared different numerics (logs: strict deterministic, TF32 off, flash attention off for 6 s); `.det` used warn-only and so did not reproduce the logs either | **Applied, except the GPU run.** `e2e.w2v2b.6s.bs16.bf16`, `e2e.xlsr.6s.bs16.bf16` and `train.w2v2b.6s.bs16.bf16.det` now use the logs' numerics: strict `use_deterministic_algorithms(True)` + `CUBLAS_WORKSPACE_CONFIG=:4096:8`, cuDNN conv TF32 off (matmul TF32 is off by default), flash SDPA off for clips longer than 4 s. Records carry `deterministic_mode`, `fill_uninitialized_memory` and every SDPA backend flag. If an op has no deterministic kernel in the friend's torch build, the child reruns the attempt once in warn-only mode and records `extra.deterministic_strict_failed`, and the report says so, so the quick suite cannot lose its headline row to this. references/README.md, reference_gpus.json, the report labels and VALIDATION.md are updated. **Rejected part: running the strict path in a second capped smoke on the RTX A4500 workstation.** The task rules allow that shared GPU for one short capped smoke only, and it was used during integration. The strict path ran on CPU (tiny `.det` row, strict, all ops have deterministic kernels) and the warn-only fallback is tested with a stub; the GPU check is listed under "not exercised" in VALIDATION.md. Test: `test_reference_numerics_rows`, `test_determinism_strict_and_warn_only`, `test_tiny_reference_numerics_row_runs_strict_on_cpu`, `test_child_reruns_warn_only_when_strict_mode_has_no_kernel` |
| R2 | medium | `e2e` clips/s = 16 / median step hides loader stalls | **Applied.** `e2e` `clips_per_s` is the wall-clock rate (clips / measured time); the median-step rate is kept as `clips_per_s_median_step` (also in comparison.csv); workload version 2; Figure 1 method line and the "How to read" box updated. Test: `test_e2e_rate_counts_loader_stalls` |
| R3 | medium | W2V2 Large and WavLM Base checkpoints never loaded with transformers 5.20 here | **Applied.** Both were downloaded on this host (CPU only) and verified (size and SHA-256); the opt-in real-weight tests now pass for all four checkpoints, and a new opt-in test runs a forward + backward pass of the real W2V2 Base classifier and of the real fusion classifier (XLS-R 300M + WavLM Base + FusionHead): 6 passed. Recorded in VALIDATION.md |
| R4 | low | `cpu.loader` reads too low when the measured batches are not a multiple of the workers | **Applied** together with F12 (whole bursts) |
| R5 | low | Windows file lock in `sanitize_file` | **Applied** (see F11) |
| R6 | low | Near-cap cuDNN / cuBLAS failures classified as errors, so the ladder stopped | **Applied.** `OOM_MARKERS` also covers "unable to find a valid cudnn algorithm", "unable to find an engine", `CUBLAS_STATUS_NOT_INITIALIZED`, `CUDNN_STATUS_NOT_SUPPORTED`; the first line of the message is kept in `extra.oom_message`.
